This Phase 7 handoff implements the original master's reusable-handler option
for the Merchant integration owner. Backend baseline is a8cb95b; the local
documentation baseline remains d97fff4. No teammate was contacted. The gRPC

## Verified wire contract

The authoritative design fixture is
[delivery.proto](../../swiftdrop-docs/api/contracts/delivery.proto), copied
unchanged into
[Contracts/Grpc/V1/delivery.proto](../src/BuildingBlocks/SwiftDrop.Contracts/Grpc/V1/delivery.proto).
Both copies have SHA-256
2BFD3102819343DB4F2407BF797D12128407B5B39AF27307503381679DCB4FC2.
They remain proposed design assets, with no generated client/server classes or
running RPC registration. The only service is swiftdrop.delivery.v1.DeliveryService:

- CreateBooking(CreateBookingRequest) returns BookingResult.
- GetBookingByExternalOrder(GetBookingByExternalOrderRequest) returns BookingResult.

CreateBookingRequest contains exactly these ten fields:

| Field | Entry adapter responsibility |
|---|---|
| merchant_id | Nonempty business UUID from the authenticated Merchant workload/job context; never a public caller's arbitrary owner |
| external_order_id | Stable nonblank order identity, at most 128 characters, retained across retries and API-key rotation |
| idempotency_key | Original stable key, retained with the job and exact payload |
| request_fingerprint | Canonical payload binding, checked against retained order identity before creating a new parcel |
| pickup_address | Address street/city/postal_code/zone_id; validate required text and eligible pickup zone |
| delivery_address | Same Address fields; validate eligibility and use its zone_id for tariff selection |
| recipient | Required Recipient name/phone_number |
| weight_kg | Exact decimal string, greater than zero and at most 30; reject malformed or excess-precision values without a double/rounded-decimal conversion |
| size | Exactly Small, Medium or Large |
| accepted_price_version | Exact validated tariff version; mismatch maps to FailedPrecondition, never silently reprice |

GetBookingByExternalOrderRequest contains only merchant_id and external_order_id.
Always query both after authorizing the business context. Another business's
same external order string is not the same resource.

BookingResult contains exactly ten fields. At initial creation the common
BookingWriteSet supplies this mapping; subsequent reconciliation must query
current authoritative Delivery parcel/history state:

| Field | Delivery source |
|---|---|
| parcel_id | Parcel.Id |
| tracking_number | Parcel.TrackingNumber generated by Delivery |
| status | Parcel.Status, initially Created |
| version | Parcel.Version, initially 1 |
| total | Snapshot.Total as an invariant exact decimal string |
| currency | Snapshot.Currency, currently LKR |
| pricing_version | Snapshot.PricingVersion |
| last_status_changed_at | Authoritative history Timestamp, initially creation time |
| terminal_at | Absent at creation; authoritative terminal-history time when applicable |
| created_at | Parcel.CreatedAt as UTC timestamp |

The REST StoredBookingResponse/Location envelope is a Customer transport result,
not the protobuf BookingResult. Do not invent a tracking read, extra wire field,
RPC, Customer quote or synthetic Customer identity to make Merchant work.

## Reusable Delivery creation and write contract

Application/Bookings/BookingAssembler exposes separate CreateCustomer and
CreateMerchant entry methods. CustomerBookingHandler uses CreateCustomer;
the future authorized internal adapter can call CreateMerchant. Both use the
same tracking generator, Parcel domain factories, price validation and Create
assembly of BookingWriteSet: Parcel, immutable PriceSnapshot, initial
BookingHistory and pending StatusChanged v1 OutboxMessage.

The Merchant entry requires the authenticated merchant ID, stable external order,
accepted pricing version, trusted audit actor UUID, validated ParcelDetails,
validated PricingTier/PriceBreakdown, tracking generator, UTC creation time and
correlation ID. Customer history derives its actor from the Customer owner.
The Merchant accepted version must match the supplied tier ordinally. Shared
assembly rejects tier/zone/size/amount mismatches and uses the same domain weight,
origin, initial-state and tracking rules. This is a post-authorization application
creation contract, not a network operation or an authentication substitute.

The exact application signatures in
[BookingAssembler.cs](../src/Services/Delivery/SwiftDrop.Delivery.Api/Application/Bookings/BookingAssembler.cs)
are:

```csharp
BookingWriteSet CreateCustomer(Guid customerId, ParcelDetails details,
    PricingTier tier, PriceBreakdown price, ITrackingNumberGenerator trackingNumbers,
    DateTimeOffset createdAt, string correlationId);

BookingWriteSet CreateMerchant(Guid merchantId, string externalOrderId,
    string acceptedPriceVersion, ParcelDetails details, PricingTier tier,
    PriceBreakdown price, Guid actorId, ITrackingNumberGenerator trackingNumbers,
    DateTimeOffset createdAt, string correlationId);
```

Before calling it, the entry adapter must authorize the workload and business,
validate both structured addresses/recipient and both active zones, resolve the
correct active destination-zone/size tariff, and verify the accepted version.
Keep exact decimals through validation. Customer retained quotes can still use
their retained tariff after an activation change; do not alter that policy to
implement the different Merchant entry validation.

Infrastructure/Bookings/BookingWritePersistence.SaveAsync requires an existing
EF database transaction before it adds any records. It saves the four booking
rows together with all pending changes in that booking-scoped DeliveryDbContext.
It never begins/commits/rolls back a transaction, authenticates, reserves a key,
calls another application service or broker, or publishes an event. The owning
adapter must add its reservation/result state in that same context/transaction and commit only after
all required writes succeed. Disposal on failure must roll back the entire write.
Its exact public signature is `Task SaveAsync(DeliveryDbContext database,
BookingWriteSet write, CancellationToken cancellationToken = default)`; see
[BookingWritePersistence.cs](../src/Services/Delivery/SwiftDrop.Delivery.Api/Infrastructure/Bookings/BookingWritePersistence.cs).

Customer PostgresBookingStore retains its owner-filtered quote lock,
principal/CreateParcel reservation, quote consumption, stored HTTP response,
commit/rollback, exception mapping and tracking-collision retry. Its IBookingStore
contract is Customer-specific; do not route Merchant through it or broaden
ICurrentCustomer into a universal service bypass. No API references another API;
the reusable code stays inside Delivery, not the dependency-free Contracts project.

## Authorization and transaction responsibilities

Service JWT validation requires the configured issuer/signature/time and exact
audience delivery-internal. CreateBooking requires bookings:create;
GetBookingByExternalOrder requires bookings:read. An internal port, role header,
unverified JWT or Merchant X-API-Key is not authorization. Merchant owns approval,
API-key scope/revocation and durable order acceptance in its own database.
Delivery must not query Merchant or Identity SQL.

The future Delivery Merchant transaction must durably reserve the stable
(merchant_id, external_order_id) identity, compare the complete canonical
fingerprint, and retain a reproducible original result. Same identity/payload
returns the existing booking; changed payload returns AlreadyExists. API-key
rotation or the Customer 30-day replay window cannot release that lifetime order
identity. The existing unique parcels index is a final guard, not a complete
fingerprint/replay implementation. Its rejection must roll back the losing
snapshot/history/outbox and must not be reported as successful replay by itself.

Resolve an existing merchant/order result before constructing a new write set
or validating the current active tariff. An identical committed replay uses its
retained result even if active pricing has since changed; it must not create or
reprice a parcel.

Permanent Merchant reservation/result storage and its concurrency/error handling
belong to the adapter integration. No new table, migration or parallel Merchant
parcel-creation policy is included here. The shared write primitive allows that
adapter to commit deduplication state with the same four Delivery booking rows.

## Unknown outcomes and failure mapping

Merchant first commits its durable inbox job and returns asynchronous 202, with
no fabricated parcel/tracking ID. Use a five-second deadline and cancellation
for the internal calls, and propagate a noncredential correlation ID. Following
DeadlineExceeded/Unavailable or loss of a response after commit:

1. Keep the job Retrying with the original merchant/order identity, key and payload.
2. Call GetBookingByExternalOrder under bookings:read.
3. An existing result finalizes Created; never mark a committed parcel Failed
   because an earlier response was lost.
4. Only a definite NotFound permits retrying CreateBooking with the same identity,
   fingerprint and key. Do not replace the order or compensate by deleting a parcel.

InvalidArgument maps invalid required input. Unauthenticated/PermissionDenied
stops processing for credential/scope remediation. AlreadyExists is a permanent
changed-payload conflict; FailedPrecondition reports pricing-version/business
state rejection. Capacity retries require a documented transient code; this
phase adds no capacity endpoint. See the exact
[gRPC semantics](../../swiftdrop-docs/api/grpc-services.md),
[UC-02](../../swiftdrop-docs/requirements/use-case-specifications.md#uc-02-merchant-order-through-secured-api)
and [service call matrix](../../swiftdrop-docs/architecture/service-catalog.md).

## Decisions and remaining owner acceptance

The fixture does not specify the Merchant fingerprint's exact serialization/hash
recipe, provisioned workload-to-job/business binding, or service subject-to-audit
UUID mapping. Agree these with the Merchant/IAM owners before enabling the RPC.
Do not reuse the Customer quote fingerprint as though it were the Merchant wire
recipe, accept a body-supplied actor, or invent a fixed production service UUID.

Member 7's integration acceptance must exercise actual service JWT failures,
business isolation, same/changed/concurrent external orders, key rotation,
retained results, pricing-version rejection and a lost committed gRPC response
followed by reconciliation. Local shared-write tests establish the reusable
creation/transaction seam only. No live gRPC, Merchant inbox, JWT, broker publish,
Neon deployment or hosted CI success is implied by those tests.
